## 1. 할 것

### P0 재기 — 앱이 스스로

- 화면을 누른 순간 → 내용이 뜬 순간을 폰에서 잰다(앱을 처음 열 때는 열기 시작부터). 남기는 건 **화면 경로(손님 id 는 ':id' 로 지움) · 밀리초 · 받아 둔 화면이었나** 뿐 — 이름 · 번호 · 손님 정보 없음.
- 매일 감시(sync-health)가 지난 7일 화면별 **보통(중간값) · 느린 때(10번 중 가장 느린 1번)** 와 매장별 **화면 연 수 · 연락 수**(숫자만)를 출력한다 — 운영자가 맥에서 따로 돌릴 것이 없고, 저도 GitHub 기록에서 읽어 다음 단계를 정한다. v6 P2 · P3 를 정할 숫자도 여기서 나온다.
- 기록이 실패해도 화면엔 영향이 없다(오류 기록과 같은 방식).
- 마이그레이션 `0024` 1개 — 기록 종류에 '속도' 추가 + 감시 함수에 속도 · 사용 수. 운영자 SQL 실행 1회.

### P1 덜 받기 — 확실한 것 셋

- **통계**: 거래 전체 → 최근 2년만. 누적 거래 수는 세기만 한다(건수 질의). 화면 숫자는 그대로(같은 결과 테스트).
- **추천 시술 근거**: 수집 기준일마다 한 번 계산해 작은 표에 저장해 두고, 홈 · 상세보기는 그걸 읽는다. 다음 수집 뒤 처음 여는 화면이 다시 계산한다(맥을 고칠 필요 없음). 같은 마이그레이션 `0024` 에 표를 함께 둔다.
- **챙길 고객**: 차례로 받던 단계 중 서로 기다릴 필요 없는 것끼리 겹쳐 받는다.

### P2 재 보고 다음

- 가장 느린 화면부터 — 후보: 고객 목록(전 고객 이름 · 번호 복호화), 홈(전 고객 + 1년 거래). P0 숫자를 보고 정한다.
- v6 P2(주간 알림) · P3(내 말투로) — P0 의 매장별 화면 연 수 · 연락 수가 1~2주 쌓이면 정한다.

## 2. 하지 않을 것

- **브라우저에 손님 이름 · 번호 저장** — 빨라지더라도. 폰을 잃어버리면 그대로 남는다.
- **외부 성능 측정 서비스** — 지금 길(운영 기록 + 매일 감시)로 충분하다.
- **수집을 더 자주** — 약관 리스크로 주 1회 유지.

없다 — 재는 일이 P0 이다. 다만 `0024` SQL 을 실행해야 기록이 쌓인다(실행 전에는 조용히 건너뛴다).

## 5. 정해야 할 것

1. 속도 기록 — **넣는다(경로 · 밀리초만, 추천)** / 안 넣는다
2. 감시 출력에 매장별 사용 수 — **넣는다(화면 연 수 · 연락 수, 숫자만, 추천)** / 속도만
3. 추천 시술 근거 — **수집 기준일마다 한 번 계산해 저장(추천)** / 지금처럼 매번
4. 순서 — **P0 먼저 2~3일 재고 P1(추천 — 전후를 숫자로 보여드릴 수 있다)** / 한꺼번에
