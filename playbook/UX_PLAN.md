# UX 계획 v2 — 덜어내고, 궁금한 걸 바로 답한다

> 대상: 1인 디자이너 3명 · 폰 · 응대 직전/직후 30초 · 데이터는 주 1회(일 14:00) 갱신
> 근거: 2026-10-12 코드·스키마 실사 — 화면(`web/app`) 전체, 마이그레이션 0001~0022, 워커 수집 필드
> 이전 계획(`UX_PROMPT.md` §2의 1~5)은 모두 반영 끝. 이 문서가 다음 단계다.

## 0. 원칙

1. **질문 하나에 화면 하나.** 같은 목적지로 가는 길은 하나만 둔다.
2. **손님에게 연락하는 순간까지 앱이 데려간다.** 지금은 문구 복사 → 앱 전환 → 손님 검색까지 사람이 한다.
3. **데이터는 일주일 묵은 사진이다.** 기준 시각을 밝히고, 추정은 추정이라고 쓴다.

## 5. 시작 전에 잴 것 (추측하지 않는다)

읽기 전용 점검 스크립트로 실제 숫자를 먼저 본다. `gap_check.py`·`gender_probe.py`와 같은 방식이다. 숫자가 작으면 비율 대신 건수를 보여줘야 해서 화면 설계가 달라진다.

```bash
cd ~/Dev/Mirrorball && .venv/bin/python worker/ux_probe.py
```

`worker/ux_probe.py` — 챙길 고객·예약·이탈 판정은 화면(`web/lib`)과 같은 기준으로 센다. 전화번호는 '있는지'만 세고 출력하지 않는다. 끝에 세 매장 합산 판단이 나온다.

- 전화번호가 있는 고객 비율 → C1·C5가 얼마나 쓸모 있는지
- `transactions.time` 채움률 → D4가 가능한지
- 방문 2회 이상(실제 주기 계산 가능) 고객 비율 → B2 중 추정이 차지하는 몫
- 선불 잔액이 남은 고객 수 → D6·A3
- 예약 상태 분포(예약·취소·노쇼) → A4를 할 가치가 있는지
- 디자이너별 월 신규 수 → D2를 %로 보여줄 만한지
- 챙길 고객 중 이미 예약한 사람 수 → 1-1이 실제로 얼마나 터지고 있는지

## 6. 정해야 할 것

모두 2026-10-12에 추천대로 정했다.

1. `/expose`와 '콘텐츠 제안' → **삭제** (노출 측정이 꺼져 있고, 리뷰 요청은 이미 한 번 뺐던 기능)
2. '소개' 탭 → **설정 안으로** (탭 4개)
3. 연락 버튼 → **문자와 전화 둘 다** (전화번호 99~100%)
4. '연락함' → **14일** 동안 할 일에서 뺀다. 문자·전화·복사 중 무엇을 눌러도 기록되고, 카드에서 되돌린다.
   연락했다고 이탈 위험이 풀리진 않으므로 손님 상태(타일·필터) 숫자에는 영향이 없다.
