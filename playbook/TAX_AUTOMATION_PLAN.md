## 1. 요약 (Executive Summary)

### 문제 — 세무사 야근의 핵심은 '입력'이 아니라 '반복적 판단'

수임처의 신용카드 매입을 어느 계정과목으로 볼지 결정하는 일이 "제일 반복적이고 오래 걸리는 일"이다. 핵심은 타이핑이 아니라 판단이다. 같은 카드 사용도 회사(업종)·대표 성향·직원 유무에 따라 처리가 갈리고, 그중 부가세 공제 여부가 가장 어렵다. "그 판단만 돼도 일이 많이 준다"가 이 프로젝트의 출발점이다.

*(주의: 야근의 실제 주범이 전표 판단인지, 신고서 작성·검토인지, 자료 받아내기인지는 아직 미확인이다 — 열린 질문 A-1. 아래 규모 추산은 '신용카드 미추천 처리'만을 대상으로 한 것이다.)*

### 기회 — 이력이 쌓인 가맹점은 높은 확률로 자동 추천 가능

실측(비커뮤니케이션즈, 2026 상반기 신용카드 매입 **150건**):

| 지표 | 값 | 의미 |
|---|---|---|
| 미추천 건수 | **40건 (26%)** | 사람이 직접 판단해야 하는 몫 |
| 거래처코드 있음 | 69건 중 미추천 **1건** | 이력만 있으면 거의 자동 처리됨 |
| 거래처코드 없음 | 81건 중 미추천 **39건** | 미추천은 사실상 '이력 없음' 문제 |
| 예측 적중률 | 사업자번호 기준 **97%** / 종목 기준 **61%** | 가맹점 단위로 맞히면 신뢰할 만함 |

즉, **가맹점(사업자번호) 단위로 과거 판단을 재사용하면 97% 수준으로 추정 가능**하다. 이것이 분류 엔진의 근거다.

### 자동화 상한 (숨기지 않고 명시)

- 미추천 40건은 **전부 과거 이력이 없는 신규 가맹점**이다. 고유 31곳, 그중 **1회성이 25곳**.
- 체인점 정규화로 커버되는 곳은 **8/31(25%)** 뿐. 나머지는 대부분 개인 음식점으로 보여 다른 수임처 이력에도 없을 가능성이 높다(추정 — 확정 아님).
- **접대 판정은 데이터만으로 불가능**하다: 같은 커피전문점이 촬영비 7 : 접대비 8, 편의점이 촬영비 5 : 소모품비 5로 갈린다. '누구와 갔는지'가 영수증에 없기 때문이다.

→ 엔진은 이력 있는 건을 자동화하고, **신규·1회성·접대성 건은 "미확인"으로 남겨 사람에게 넘긴다.** 100% 자동 분류를 주장하지 않는다.

### 규모 추산

| 범위 | 추산 |
|---|---|
| 신용카드 미추천만 | 거래처당 월 7건 · 136곳이면 **월 약 5시간** |
| 통장·세금계산서·현금영수증도 같은 구조라면 | **월 20~25시간(4~5배)** |

후자는 아직 가정이다 → 아래 '다음에 받을 것'으로 검증한다.

### 접근 — 엔진 먼저, 자동화(다운로드)는 마지막

1. **분류 엔진 + 공용 사전**이 엑셀 몇 개로 실제 쓸모가 있는지 먼저 증명한다.
2. 쓸모가 확인되면 그때 저부하 자동 다운로드로 감싼다. 엔진이 별로면 다운로드는 의미 없다.

**넘지 않는 선(반출·약관):**
- WEHAGO 자동 다운로드는 크롤링 금지 조항이 '없다'지만 회색지대다 — 하루 1회·자기 자료만·영업시간 회피의 저부하 가드레일로 설계하고, 실서비스 전 개별약관(WEHAGO T) 재확인. 순서상 **마지막 단계**.
- **HandSOS 수집은 약관 위반으로 중단 상태 — 재가동 금지**(WEHAGO와 혼동 금지).
- **국세청 자료 삭제 후 엑셀 재업로드는 권장하지 않음** — 엑셀분은 별개 계열이라 국세청 자료를 대체하지 못하고 공제/불공제 수정도 불가. 실무자 확인 전 금지.
- 주민등록번호는 저장하지 않는다(개인정보보호법 24조의2) — 스키마에 컬럼 자체가 없다.
- WEHAGO 기존 기능(휴폐업조회·오류검증·공제유형별 집계·부가세신고요약·전자중복·체크카드 감지 등)은 **중복 개발하지 않는다.**

## 2. 업무 자동화 영역 전체 맵

세무대리인이 실제로 반복하는 업무 A~E를 자동화 가능성 기준으로 정리한다. 핵심은 "입력"이 아니라 **판단**의 자동화이며, 회사(업종)·대표 성향·직원 유무에 따라 같은 거래도 처리가 갈린다. 아래 수치는 전부 실측(비커뮤니케이션즈 2026 상반기 신용카드 매입 150건)과 근거 파일에서 인용했고, 지어낸 값은 없다.

### 2.1 전체 요약표

| 업무 | 현재 방식 | 자동화 가능성 | 추정 가능한 부분 | 사람이 남는 상한 | 근거 |
|---|---|---|---|---|---|
| **A. 신용카드 → 계정과목 분류** | WEHAGO에서 미추천 건을 하나씩(또는 일괄변경) 계정 지정. 업종·사람·직원 유무로 처리 상이. "제일 반복적이고 오래 걸리는 일" | **부분(이력 건 한정 높음)** | 이력 있는 가맹점은 **사업자번호 기준 97% 적중**. 코드 있는 69건 중 미추천은 1건뿐 | **3% + 신규·접대 판정** (아래 2.2) | 통화 A, 실측 150건(비커뮤니케이션즈) |

### 2.2 A(신용카드 분류)의 자동화 상한 — 숨기지 않고 명시

**추정되는 97%.** 과거 이력이 있는 가맹점은 사업자번호 기준 계정 예측 적중률이 97%다. 반대로 **종목 기준으로는 61%**로 뚝 떨어진다 — 즉 "무슨 업종인가"가 아니라 "이 가맹점을 전에 어떻게 처리했나"가 정확도를 만든다. 그래서 이력이 붙는 거래는 거의 자동으로 채울 수 있다(코드 있는 69건 중 미추천 1건).

**남는 3% + 신규·접대 판정 — 데이터만으로는 못 넘는 벽.** 150건 중 미추천 40건(26%)이 나왔고, 그중 39건이 코드 없는 81건에서 나왔다. 이 **미추천 40건은 전부 과거 이력이 없는 신규 가맹점**이다.

- **신규·1회성 문제:** 고유 31곳, 그중 **25곳이 1회성**. 체인점 정규화로 커버 가능한 곳은 **8/31(25%)**뿐이고 나머지는 개인 음식점이라 다른 거래처 이력에도 없을 가능성이 높다. 사전(공용 사전)으로도 채워지지 않는다.
- **접대 판정 불가:** 같은 종목이 갈리는 사례 — 커피전문점 → 촬영비 7 : 접대비 8, 편의점 → 촬영비 5 : 소모품비 5. **"누구와 갔는지"가 영수증에 없어 데이터만으로는 판정 불가**다. 이 부분은 원리상 자동화가 아니라 사람이 남는 구간으로 설계해야 한다(추측 계상은 세무상 문제 → A-3 미해결).

**규모 감(추정).** 신용카드 미추천만 보면 거래처당 월 7건, 136곳이면 **월 약 5시간**. 통장·세금계산서·현금영수증도 같은 구조라면 **월 20~25시간(4~5배)**. 단 이 배수는 아직 추정이며, 엑셀 3개(통장·세금계산서·현금영수증)를 받으면 직접 계산해 확정할 수 있다(A-2 미해결).

### 2.3 지도에 표시된 금지선 (이 맵 밖으로 나가지 말 것)

- **WEHAGO 자동 다운로드는 맨 마지막.** 먼저 분류 엔진 + 공용 사전이 엑셀 몇 개로 쓸모를 증명한 뒤에만 저부하(하루 1회·자기 자료만·영업시간 회피·요청 지연) 다운로드로 감싼다. 약관에 명시 금지는 없으나 이는 "회색지대가 좁다"는 뜻이지 허용이 아니며, 실서비스 전 개별약관(WEHAGO T) 재확인이 전제다.
- **HandSOS 수집은 재가동 금지**(약관 19조1항17호 스크래핑 금지로 중단 상태). WEHAGO와 혼동하지 말 것.
- **국세청 자료 삭제 후 엑셀 재업로드 금지.** 엑셀분은 `자료구분=엑셀` 별개 계열이라 국세청 자료를 대체하지 못하고 공제/불공제 수정도 불가 → 실무자 확인 전 시도 금지(C-1).
- **주민등록번호는 컬럼 자체를 두지 않는다**(개인정보보호법 24조의2). 앱은 연락·자료요청 관리 목적에 필요한 항목만 받는다.
- **WEHAGO 기존 기능은 중복 개발 금지:** 휴폐업조회·오류검증·공제유형별 집계·부가세신고요약·고정자산확인·면세확인·세액확인·전자중복·체크카드 감지.

> 지도 요약: **A가 유일한 "판단 자동화" 코어**(이력 건 97% 추정 / 3%+접대 판정은 사람), **B는 상태추적·알림으로 즉시 가치**(스키마 준비 완료), **C는 쉬운 배관이나 반출 안전성 확인이 관문**, **D는 미래 시즌용**, **E는 우리 영역 아님**. 만들기 시작할 순서는 A(엔진)+B(사전·추적)를 엑셀로 증명 → 그다음 저부하 다운로드.

### P0-1. 신용카드 계정과목 추천/분류 엔진

**무엇을** — WEHAGO에서 반출한 **매입 엑셀서식(13컬럼)** 을 입력받아, 가맹점 이력 사전으로 각 건의 차변계정코드를 추천한다. 추천 가능한 건은 채워서 되돌려주고, **미추천만 사람 큐로 몰아준다.** 사람은 전체를 훑지 않고 큐만 처리한다.

- 입력 컬럼: 거래일자·거래처(가맹점명)·사업자번호·품명·유형·공급가액·세액·봉사료·합계·차변계정코드·대변계정코드·공제여부·거래구분
- 추천 키 = **사업자번호(가맹점) 우선, 품명 보조.** (업태·종목·거래처코드는 서식에 없으므로 키로 못 씀)
- 미추천 정의(공식 문서 기준 그대로): 거래처+품명 추천율 **50% 초과면 추천, 이하/무이력이면 미추천.**

**왜 지금 가능** — "제일 반복적이고 오래 걸리는 판단"이 계정과목 분류이고(통화 A), 그 판단 상당수는 **과거 이력이 있으면 결정적**이다. 실측이 이를 뒷받침한다.

| 실측 (비커뮤니케이션즈 2026 상반기 신용카드 매입 150건) | 값 |
|---|---|
| 전체 매입 | 150건 |
| 미추천 | 40건 (26%) |
| 거래처코드 있음 → 미추천 | 69건 중 **1건** |
| 거래처코드 없음 → 미추천 | 81건 중 **39건** |
| 예측 적중률 — 사업자번호(가맹점) 기준 | **97%** |
| 예측 적중률 — 종목 기준 | 61% |

→ 사업자번호로 매칭되면 97% 적중이므로, **이력 사전만 있으면 대부분 자동 추천**되고 사람은 26%(미추천)만 본다.

**단, 자동화 상한을 숨기지 않는다 (반드시 인지):**

- **미추천 40건은 전부 과거 이력 없는 신규 가맹점.** 고유 31곳, 그중 **1회성 25곳.** → 학습으로 줄지 않는 잔여가 크다.
- 체인 정규화로 커버 가능한 곳은 **8/31(25%)뿐.** 나머지는 개인 음식점이라 타 거래처 이력에도 없다.
- **접대비/촬영비·소모품 판정은 데이터만으론 불가.** 커피전문점 → 촬영비 7 : 접대비 8, 편의점 → 촬영비 5 : 소모품 5 로 갈린다. **'누구와 갔는지'가 영수증에 없어** 기계가 못 정한다. → 이런 건은 **추천하지 말고 미추천 큐로** 넘겨 사람이 정한다(틀린 추천보다 낫다).
- WEHAGO **거래처 자동생성('여')로 켜면 신규가 학습되지만**, 1회성 25곳까지 영구 거래처로 오염된다. → **실무자 확인 전 건드리지 않는다**(TAX_QUESTIONS B-1).

**기존 자산 재사용**

- **엑셀 왕복 경로**(반출 `엑셀로 변환` / 반입 `매입엑셀서식 불러오기`)는 WEHAGO 정식 기능. 사람이 누르는 방식이라 약관 저촉 없음.
- WEHAGO 기존 기능과 **중복 개발 금지**: 휴폐업조회·오류검증·공제유형별 집계·부가세신고요약·고정자산확인·면세확인·세액확인·전자중복·체크카드 감지. 우리는 **"미추천 계정 채우기"만** 한다.
- `clients.tags`·`memo` 로 거래처별 성향(통화 A: 회사 업종·직원 유무로 처리가 갈림)을 규칙에 반영할 여지.

**완료 정의 (DoD)**

- [ ] 13컬럼 엑셀 입력 → 사업자번호 사전 매칭 → 차변계정코드 채운 엑셀 출력
- [ ] 미추천(무이력·추천율 50% 이하·판정불가 후보)은 **빈 채로 별도 '미추천 큐' 시트**에 분리
- [ ] 접대성 후보(커피·편의점 등 종목 갈림)는 자동 확정하지 않고 큐로
- [ ] **재현 테스트**: 비커뮤 150건 재투입 시 미추천 40건 재현, 코드 있음 69건 중 68건 자동 채움
- [ ] 출력물은 **반입 서식과 100% 호환**(사람이 WEHAGO에 `불러오기` 가능). 국세청 자료 삭제·대체 없음

**예상 효과**

- 사람이 보는 건수 150 → **40(미추천만)** 으로 축소. 추정 규모: 신용카드 미추천 기준 거래처당 월 7건, 136곳이면 **월 5시간.**
- **미확정(열린 질문):** 통장·세금계산서·현금영수증도 같은 구조면 월 **20~25시간(4~5배)** 가능. 단 A-2(타 자료 미추천 비율)·A-1(야근 실제 원인)이 아직 미해결이라 효과는 **엑셀 3개 받아 직접 계산해 검증**한 뒤 확정한다. **지금 실측으로 확인된 것은 150건 표본의 미추천율(26%)·사업자번호 매칭 적중률(97%)까지**이고, 월 5시간은 이를 거래처당 7건×136곳으로 확장한 **추산 하한(실측 아님)** 이다.

### P0-2. 자료요청 체크리스트 + 리마인더

**무엇을** — 수임처별로 "무엇을 언제 요청했고, 받았는지/안 받았는지"를 기록하고, **받은 데 체크·안 받은 데 알림.** 아버지(실무자)의 **명시 요청**(통화 B)이다.

- 요청 종류: 인건비 · 현금증빙 · 계약서 · 재고 · 기타
- 상태: `requested_at`(요청) / `received_at`(null이면 미수취 → 독촉 대상)

**왜 지금 가능** — 스키마가 **이미 존재**하고, 기억에만 있던 것을 테이블로 옮기는 단순 작업이라 신규 리스크가 없다. "데이터가 좀 쌓여야 문제점이 나온다"(통화 B)는 특성상, **일찍 시작해 반복 사용하며 개선**하는 게 맞다.

**기존 자산 재사용** — 새로 만들 스키마가 거의 없다.

| 자산 | 재사용 |
|---|---|
| `doc_requests`(period·kind·requested_at·received_at) | 그대로 |
| `doc_requests_open_idx` (`received_at is null` 부분 인덱스) | **미수취 목록 쿼리 = 리마인더 소스** |
| `clients`(수임처 마스터·`churned_at`) | 대상 수임처 = 활성 clients |
| `contacts`(channel·summary) | 독촉 접촉 이력 기록 |
| RLS/암호화 (미용실과 동일, C1/M1 잠금 포함) | 그대로 |

**완료 정의 (DoD)**

- [ ] 수임처 × 기간(`YYYY-MM`) × 종류로 요청 등록, `received_at` 체크로 수취 처리
- [ ] "이번 달 미수취" = `received_at is null` 목록 화면(부분 인덱스 활용)
- [ ] 독촉 리마인더: 미수취 목록을 담당자에게 알림(주기·채널은 실무자 확인 후 확정)
- [ ] 개인정보: 주민등록번호 **컬럼 자체 없음** 유지(PIPA 24조의2), PII는 `pii_enc`로만

**예상 효과**

- "다 기억 못 함"(수임처 다수)을 시스템이 대신 기억 → 누락·중복 요청 감소.
- **주의:** 자료가 끝내 안 올 때의 처리(A-3: 보수적 계상/가지급금/불인정/불공제)는 미해결. 리마인더는 "받아내기"까지만 돕고, **미수취 후속 처리는 사람 판단.**

## 4. 나중에 할 수 있는 것 (Later · P2+)

> 이 단계는 전부 **P1(신용카드 분류 엔진 + 공용 사전)이 엑셀 몇 개로 쓸모를 증명한 뒤**에 착수한다. 순서를 지키는 이유는 아래 각 항목의 '선행조건'에 적었다. 엔진이 별로면 확장·다운로드는 의미가 없다.

### 4.1 분류 엔진을 다른 자료로 확장 (통장·전자세금계산서·현금영수증)

신용카드에서 검증된 "거래처+품명 → 계정과목 추천" 로직을 나머지 자료 계열로 넓힌다. 이게 이 프로젝트의 규모를 가르는 지점이다.

| 항목 | 값(실측/추정) |
|---|---|
| 신용카드 미추천만 | 거래처당 월 7건 · 136곳이면 **월 5시간** |
| 통장·세금계산서·현금영수증이 같은 구조면 | **월 20~25시간 (4~5배)** |
| 근거 실측(비커뮤니케이션즈 2026 상반기 신용카드 매입 150건) | 미추천 40건(26%) · 코드 있음 69건 중 1건 / 코드 없음 81건 중 39건 |

- **효과가 4~5배라는 건 아직 가정이다.** 통장·전자세금계산서·현금영수증의 미추천 비율이 신용카드(26%)와 비슷한지 확인되지 않았다(열린 질문 A-2).
- **선행조건 (착수 전 증명돼야 할 것):**
  - **A-2 확인** — 통장·전자세금계산서·현금영수증 **엑셀 3개**를 받아 미추천 비율을 우리가 직접 계산. 신용카드와 비슷하게 나와야 "월 20~25시간"이 성립한다.
  - **A-1 확인** — 야근의 실제 원인이 전표 처리(=이 작업)인지. 자료 받아내기·신고서 검토가 주범이면 확장보다 **자료 수취관리(통화 B, P1 영역)**가 우선이다.
  - P1 신용카드 엔진이 실제 반출용 13컬럼 엑셀(거래일자·거래처·사업자번호·품명·유형·공급가액·세액·봉사료·합계·차변계정코드·대변계정코드·공제여부·거래구분)로 쓸모를 증명.

### 4.2 자동화 상한 — 확장해도 못 넘는 벽 (숨기지 말 것)

자료를 늘려도 아래는 데이터만으로 해결되지 않는다. 확장 항목의 기대치를 여기에 맞춰 잡아야 한다.

| 벽 | 실측 근거 | 함의 |
|---|---|---|
| **신규 가맹점** | 미추천 40건 **전부** 과거 이력 없는 신규 가맹점 | 이력 학습으로 못 잡음 |
| **1회성** | 고유 31곳 중 **1회성 25곳** | 거래처 마스터에 남길 가치도 애매 |
| **체인 정규화 한계** | 커버 8/31 (**25%**) | 나머지는 개인 음식점이라 타 거래처 이력에도 없음 |
| **접대 판정 불가** | 커피전문점 촬영비7:접대비8 / 편의점 촬영비5:소모품5 | **'누구와 갔는지'가 영수증에 없어 데이터만으로 판정 불가** |

- 반대로 강한 부분: 예측 적중률은 **사업자번호(가맹점) 기준 97%**, **종목 기준 61%**. 즉 값은 "이미 아는 가맹점"에서 나오고, 미추천의 본질은 신규·1회성이다.
- 결론: 확장의 목표는 "미추천 0"이 아니라 "이력 있는 건을 자동으로 치우고, 신규·1회성·접대 건만 사람 앞에 남기는 것".

### 4.3 급여 기본세팅 (소득세·법인세 시즌)

부가세 시즌이 아니라 **소득세·법인세 시즌**을 겨냥한 별개 트랙. 통화 D에서 나온 "부가세로 안 간 전표 + 급여(종류 다양) 회계 입력 — 기본 세팅만 해줘도 수월"에 해당한다.

- **범위**: 부가세 단계에서 처리 안 된 전표 정리 + 급여의 기본 회계 입력 세팅. "완전 자동"이 아니라 **기본 세팅 보조**.
- **선행조건:**
  - 급여 항목의 "종류가 다양하다"의 실체 파악 — 어떤 유형이 몇 개고 회사·직원 유무별로 어떻게 갈리는지(통화 A의 "회사·사람 특성·직원 유무로 처리가 달라짐"과 같은 구조).
  - 4.1이 돌아가서 "이력 있는 건 자동 분류" 패턴이 이미 검증돼 있을 것(같은 판단 로직을 재사용).
- **범위 밖(자동화 대상 아님)**: 4대보험·은행 대출서류 등 잡무는 통화 E대로 제외. "AI가 할 수 있는 게 아님"이며 전자문서(신고번호로 당겨오기)로 이동 중.

### 4.4 국세청 오픈API로 휴폐업·과세유형 자동확인

`clients` 테이블에 이미 자리가 있다(`tax_type`, `biz_status`, `status_checked_at`). 국세청 오픈API로 이 두 값을 채운다.

- **채우는 값**: `tax_type`(일반·간이·면세) / `biz_status`(계속사업자·휴업·폐업) + 조회 시각(`status_checked_at`).
- **중복 개발 금지**: WEHAGO에 **휴폐업조회**가 이미 있다. 이건 WEHAGO 안에서 하는 게 아니라, **우리 앱의 수임처 목록**(`clients`)을 스스로 최신 상태로 유지하기 위한 것 — 목적이 다르다는 걸 명확히 하고 착수.
- **선행조건:**
  - 앱에 유지할 실제 수임처 목록(`clients`)이 온보딩돼 있을 것(`worker/onboard_tax.py`로 테넌트 생성 후).
  - 국세청 오픈API의 필드가 `일반·간이·면세` / `계속사업자·휴업·폐업` 스키마에 그대로 매핑되는지 확인.
- **금지선**: 주민등록번호는 저장하지 않는다(개인정보보호법 24조의2 — 스키마에 컬럼 자체 없음). API 응답에 섞여 와도 저장하지 말 것.

### 4.5 WEHAGO 저부하 자동 다운로드 (**마지막 단계**)

수임처별 자료 다운로드를 배치로 자동화해 4.1 엔진에 먹인다. **가장 마지막**이고, 법적 가드레일 없이는 착수 금지.

- **순서 원칙(반드시)**: 자동 다운로드는 마지막에. 먼저 **분류 엔진 + 공용 사전이 엑셀 몇 개로 쓸모를 증명** → 되면 그 위를 저부하 다운로드로 감싼다.
- **법적 상태(2026-07-22 판단, 변호사 판단 아님):**
  - ID/PW 로그인(인증서 아님), 약관에 크롤링·스크래핑 **명시 금지 조항 없음**, 세무대리인 **본인 계정**, 개인용·비상업.
  - 남는 리스크는 **9조②1호 "서비스에 현저한 지장" 하나**뿐.
- **가드레일(설계 필수 조건)**: **하루 1회 상한 · 수임처별 자기 자료만 · 저부하(요청 간 지연, 영업시간 회피)**. "현저한 지장"은 결과 요건이라 이 셋으로 회피.
- **선행조건:**
  - 4.1 엔진이 엑셀 몇 개로 쓸모 증명 완료.
  - 실서비스 전 **개별약관(WEHAGO T) 재확인** — "명시 금지 없음"은 회색지대가 좁다는 뜻이지 허용은 아니다.
- **혼동 금지 / 금지선(제안하면 안 되는 것):**
  - **HandSOS는 재가동 금지** — 약관 19조1항17호(스크래핑 금지)로 수집 **중단** 상태. WEHAGO와 다른 서비스다. 둘을 섞지 말 것.
  - **국세청 자료 삭제 후 엑셀 재업로드 금지** — 엑셀분은 `자료구분=엑셀` 별개 계열이라 국세청 자료를 대체하지 않고, 공제/불공제 수정이 불가하다. **실무자가 명확히 문제없다고 하기 전엔 시도 금지**(열린 질문 C).

**중복 개발 금지 확인 필요** — WEHAGO에 이미 있는 기능은 다시 만들지 않는다: 휴폐업조회, 오류검증, 공제유형별 집계, 부가세신고요약, 고정자산 확인, 면세확인, 세액확인, 전자중복, 체크카드 감지.

### 5.4 넘지 말아야 할 금지선 (약관·법)

- **WEHAGO 개별약관(WEHAGO T) 재확인 — 자동 다운로드는 회색지대, 허용 아님.**
  2026-07-22 판단: ID/PW 로그인(인증서 아님), 약관에 크롤링·스크래핑 **명시 금지 조항 없음**, 세무대리인 **본인 계정**, 개인용·비상업. 남는 리스크는 **9조②1호 "서비스에 현저한 지장" 하나** → **하루 1회·수임처별 자기 자료만·저부하(요청 지연·영업시간 회피)** 가드레일로 회피.
  - **왜 미정** — "명시 금지 없음 = 회색지대가 좁다"는 것이지 허용이 아니다. 사람이 엑셀변환을 누르는 것과 프로그램이 자동으로 누르는 것은 법적으로 다르다. 개별약관(WEHAGO T)은 아직 재확인 안 됨.
  - **결정되면** — 개별약관에 스크래핑 금지가 있으면 자동 다운로드는 **폐기**. 없으면 저부하 가드레일로 감싼다. **순서 원칙: 자동 다운로드는 마지막.** 먼저 분류 엔진+공용 사전이 엑셀 몇 개로 쓸모를 증명하고, 되면 그때 저부하 다운로드로 감싼다. 엔진이 별로면 다운로드는 의미 없다.

- **국세청 자료 대체 금지 (C-1과 연동).** 국세청 수집분을 지우고 엑셀로 덮는 방식은 별개 계열이 되고 공제/불공제 수정도 불가하므로 **실무자 확인 전 금지**. 이 선은 제품 기본값으로 못 박는다.

- **HandSOS 수집 재가동 금지.** HandSOS는 약관 **19조1항17호(스크래핑·"모든 시도" 금지)** 로 수집 **중단** 상태(중단 일자는 원문 재확인 필요). 위반 시 사전 통지 없이 계약 해지·서비스 중지되고 **잃는 쪽이 매장**(예약·매출·고객). **다른 세션/작업자 포함 재가동 금지.** 재개는 (주)예스오예스 서면 승낙 또는 정식 반출 경로/매장 직접 내보낸 파일로 전환한 뒤에만. **WEHAGO와 혼동하지 말 것** — 둘은 약관이 다르다.

- **주민등록번호 미저장 (개인정보보호법 24조의2).** 앱 스키마(`clients`)에 주민번호 **컬럼 자체를 두지 않는다** — 실수로라도 들어갈 자리를 만들지 않기 위해서다. 같은 이유로 주소·업종코드 등 목적(연락·자료요청 관리)에 불필요한 항목도 받지 않는다. `pii_enc`에 담는 건 대표자명·연락처·담당자 정보뿐이고 테넌트 자체 DEK로만 열린다(`onboard_tax.py`). **이 원칙은 협상 대상이 아님.**

### 5.5 회사 고유 계정과목 — 거래처별 계정표 확보 방법 (미해결)

계정과목 추천 도구가 성립하려면 **거래처별 계정과목표**가 있어야 하는데, 지금은 얻을 경로가 없다.

- **왜 미정** —
  - 표준 코드표에 없는 계정이 실재한다: `(제)촬영비`는 화면 분개에서 **528**로 표시됐고, SmartA10에서 계정명을 수정하면 **그 회사 전용 코드**를 써야 한다고 서식에 명시돼 있다.
  - 그런데 **엑셀 서식 13컬럼(거래일자·거래처(가맹점명)·사업자번호·품명·유형·공급가액·세액·봉사료·합계·차변계정코드·대변계정코드·공제여부·거래구분)에는 업태·종목·거래처코드가 없다.** 즉 반출 엑셀만으로는 "이 회사가 528을 촬영비로 쓴다"는 매핑을 복원할 수 없다.
- **결정되면 바뀌는 것** —
  - 거래처별 계정표를 확보하면(예: 회사별 계정과목표를 별도로 내려받거나 실무자가 초기 세팅으로 등록) → 추천을 **회사 고유 코드로 정확히** 낼 수 있다.
  - 확보 경로가 없으면 → 추천은 **표준 계정 수준까지만** 내고 고유 계정(촬영비 등)은 사람이 확정하도록 남긴다. 이 경우 종목 기준 적중률 **61%**의 한계가 그대로 노출되므로, 도구는 "확정"이 아니라 "초안 제시"에 머문다.

> 확보 방법 자체가 아직 **정해지지 않은 열린 항목**이다. 이걸 풀기 전에는 계정 추천 도구를 "자동 확정"으로 광고하지 않는다.

## 6. 프로젝트 계획 (마일스톤·KPI·아키텍처·리스크)

### 6.0 계획의 전제 — "엔진 우선, 다운로드 마지막"

이 프로젝트는 **자동 수집(WEHAGO 다운로드)부터 만들지 않는다.** 순서 원칙은 명확하다: 먼저 **분류 엔진 + 공용 사전**이 엑셀 몇 개만으로 실제로 시간을 줄이는지 증명하고(M0), 쓸모가 확인되면 그때 저부하 다운로드로 감싼다(M3). 엔진이 별로면 다운로드는 의미가 없기 때문이다.

또한 이 계획은 아직 **추정 위에 서 있다.** `playbook/TAX_QUESTIONS.md`의 열린 질문 — A-1(야근의 실제 원인), A-2(다른 자료도 미추천 비율이 비슷한지), A-3(자료가 끝내 안 오면 실제 처리법), B(WEHAGO 설정을 켜도 되는지), C(엑셀 반입·재수집 안전성) — 이 미해결이다. M0의 첫 목적은 기능 개발이 아니라 **이 가정들을 실측으로 검증**하는 것이다.

### 6.1 마일스톤

|---|---|---|---|
| **M0** | 엔진 쓸모 증명 | 엑셀 3개(통장·전자세금계산서·현금영수증)로 미추천 비율·처리시간을 **직접 측정**해, 만들 가치가 있는지(월 5시간이냐 20~25시간이냐)를 숫자로 답한다 | 실측 리포트, A-2 답변 |
| **M1** | 분류 엔진 + 사전 MVP | 신용카드 매입 엑셀을 입력하면 계정과목을 추천하고, **미추천 건만 골라서** 실무자에게 제시. 사업자번호 사전 + 체인 정규화 사전 탑재 | 분류 엔진, 공용 사전, 13컬럼 서식 출력 |

> **M2 → M3 게이트:** M3의 자동 다운로드는 **엔진이 이미 쓸모를 증명한 뒤**에만 착수한다. 순서를 뒤집지 않는다.

### 6.2 이 프로젝트가 자동화하는 것 / 못 하는 것 (숨기지 않음)

신용카드 분류의 상한은 실측으로 이미 드러났다. 이건 **한계이지 흠이 아니며**, 처음부터 명시하고 설계한다.

**엔진이 잘하는 것 (실측):**
- 비커뮤니케이션즈 2026 상반기 신용카드 매입 **150건 중 미추천은 40건(26%)**.
- **사업자번호(가맹점) 기준 예측 적중률 97%** — 한 번 본 가맹점은 거의 맞힌다.
- 코드(거래처) 있는 69건 중 미추천은 **단 1건**. 이력이 쌓이면 미추천은 거의 사라진다.

**엔진이 구조적으로 못 하는 것 (자동화 상한):**
- 미추천 40건은 **전부 과거 이력이 없는 신규 가맹점**. 고유 31곳, 그중 **1회성이 25곳** — 한 번 가고 마는 곳이라 학습으로도 커버가 안 된다.
- 체인점 정규화로 커버 가능한 곳은 **8/31(25%)** 뿐. 나머지는 개인 음식점이라 타 거래처 이력에도 **없을 것으로 본다(추정).**
- **종목 기준 적중률은 61%**로 떨어진다. 같은 종목이 갈리는 사례: **커피전문점 → 촬영비 7 : 접대비 8**, **편의점 → 촬영비 5 : 소모품비 5**. "누구와 갔는지"가 영수증에 없어 **데이터만으로는 판정 불가.** 이 구간은 자동 확정이 아니라 실무자에게 넘긴다.

즉 엔진의 역할은 "모든 걸 분류"가 아니라 **"확신 있는 건 자동 추천하고, 판정 불가능한 신규·1회성·접대성 건만 사람에게 올려 판단을 돕는다"** 이다.

- 목적: 신용카드에서 본 미추천 구조가 다른 자료에서도 반복되는지(A-2) 자체 계산으로 확인.
- 출력 서식은 WEHAGO 매입엑셀서식 **13컬럼**을 그대로 따른다: 거래일자 · 거래처(가맹점명) · 사업자번호 · 품명 · 유형 · 공급가액 · 세액 · 봉사료 · 합계 · 차변계정코드 · 대변계정코드 · 공제여부 · 거래구분.
  - **주의:** 업태·종목·거래처코드는 이 서식에 없다. 엔진이 종목 기반 추천을 하더라도 최종 출력은 13컬럼 안에서만 표현된다.

### 6.5 아키텍처

기존 미용실 인프라를 **재사용**한다. 새로 만드는 건 분류 엔진과 수집 어댑터뿐이다.

**데이터 계층 — `supabase/migrations/0016_tax_domain.sql` 그대로 사용**

| 테이블 | 역할 | 이 프로젝트에서의 쓰임 |
|---|---|---|
| `clients` | 거래처(수임처) | biz_no · name · entity_type · fiscal_month · tax_type · biz_status · memo · tags · churned_at. 계정 추천의 회사 컨텍스트 |
| `doc_requests` | 자료 요청 | period · kind(인건비·현금증빙·계약서·재고·기타) · requested_at · **received_at(null=미수취)** → M2 독촉의 근거 |
| `contacts` | 접촉 이력 | channel · summary · source · ext_id. 통화·카톡 기록 |

- **RLS·암호화는 미용실과 동일 패턴 재사용** — `current_tenant_ids()` 기반 테넌트 격리, 테넌트별 자체 DEK, **C1/M1 잠금 포함.** 온보딩은 `worker/onboard_tax.py`(`industry='tax'`, 자체 DEK)로 처리.
- **개인정보 원칙(설계에 못박음):** 주민등록번호 컬럼을 **스키마에 두지 않는다**(개인정보보호법 24조의2). 대표자명·연락처 등 PII는 `pii_enc`로 암호화. 주소·업종코드처럼 목적에 불필요한 항목은 받지 않는다.
- **국세청 오픈API**로 `tax_type`·`biz_status`(휴폐업) 자동 채움 여지 — 합법적 공식 경로.

**수집 계층 — 어댑터로 추상화 (교체 가능)**

핵심 설계 결정: 엔진은 "정규화된 매입 레코드"만 입력받고, **어디서 왔는지는 모른다.** 소스는 어댑터 뒤에 숨긴다.

```
[수집 어댑터]  →  [정규화 레코드]  →  [분류 엔진 + 공용 사전]  →  [13컬럼 엑셀 / 미추천 목록]
   ├ CSV/엑셀 업로드   (M0·M1의 유일한 소스)
   ├ 공식 API          (국세청 오픈API 등)
   └ 저부하 다운로드    (M3, 약관 재확인 후에만)
```

이 추상화 덕분에 M0·M1은 **엑셀 업로드만**으로 완성되고, 자동 다운로드는 나중에 어댑터 하나만 꽂으면 된다. 수집 경로 하나가 막혀도 — HandSOS는 약관 19조1항17호(스크래핑 금지)로 수집이 **중단**됐다 — 그 리스크를 한 어댑터 안에 격리해 앱 전체로 번지지 않게 하는 구조다. (다만 어댑터 격리는 경로를 분리할 뿐, 약관 리스크 자체를 없애지는 못한다.)

**엔진 내부**
- 사업자번호 사전(가맹점 → 계정): 97% 적중의 원천.
- 체인 정규화 사전: 커버리지 상한 25%(8/31)를 명시한 채 점진 확충.
- 회사 컨텍스트 규칙: 업종·직원 유무·대표 성향에 따라 처리가 갈리므로 `clients.memo`/`tags`를 규칙 입력으로 사용.
- **거래처별 계정과목표 문제(B-3 미해결):** `(제)촬영비`처럼 표준표에 없는 회사 고유 계정이 있다. 이 매핑을 어떻게 얻을지는 실무자 확인 전까지 열린 항목으로 둔다.

### 6.6 리스크 · 가드레일

| 리스크 | 내용 | 가드레일 |
|---|---|---|
| **약관 위반(수집)** | WEHAGO 자동 다운로드. 약관에 크롤링 명시 금지는 **없으나**, 9조②1호 "서비스에 현저한 지장"이 남는 리스크 | **저부하 설계**: 하루 1회 상한 · 자기(수임처) 자료만 · 요청 간 지연 · 영업시간 회피. **M3에서만**, 실서비스 전 개별약관(WEHAGO T) **재확인 필수** |
| **회색지대 오판** | "명시 금지 없음"을 "허용"으로 착각 | 회색지대가 좁을 뿐 허용 아님. 사람이 누르는 정식 기능과 프로그램 자동 클릭은 법적으로 다름을 전제로, 자동 다운로드는 **끝까지 미룬다** |
| **HandSOS 재가동** | HandSOS는 약관 19조1항17호로 수집 **중단** 상태 | **재가동 금지.** WEHAGO와 혼동 금지 — 둘은 완전히 다른 약관 |
| **엑셀 재업로드로 국세청 자료 대체** | 국세청 자료 삭제 후 엑셀 재업로드 | 엑셀분은 `자료구분=엑셀` **별개 계열**, 국세청 자료를 대체하지 않고 공제/불공제 수정 불가 → **권장하지 않음. 실무자가 문제없다 확인하기 전엔 금지** |
| **엔진 과신(접대 판정 등)** | 데이터만으로 판정 불가능한 건을 자동 확정 | 판정 불가 구간(신규·1회성·접대성)은 자동 확정 금지, **실무자 확인 게이트**로 넘김 |
| **WEHAGO 설정 무단 변경** | 거래처 자동생성('여')을 켜면 미추천이 준다는 유혹 | 켜면 마스터 오염(1회성 25곳이 영구 거래처로 남음). **실무자 확인 없이 건드리지 않음** |
| **중복 개발** | WEHAGO 기존 기능 재구현 | 휴폐업조회·오류검증·공제유형별 집계·부가세신고요약·고정자산확인·면세확인·세액확인·전자중복·체크카드 감지는 **이미 있음 → 만들지 않음** |
| **잘못된 가정 위 개발** | A-1~A-3·B·C 미해결 상태로 확장 | M0에서 실측·실무자 확인 우선. 답 받기 전엔 M2 이후 확정 설계 보류 |

**세 가지 관통 원칙**
- **엔진 우선** — 쓸모를 엑셀로 증명하기 전엔 수집 자동화에 손대지 않는다.
- **저부하** — 자동 다운로드는 하루 1회·자기 자료·저부하로만.
- **실무자 확인 게이트** — 판정 불가 건, WEHAGO 설정, 국세청 자료 반입은 전부 사람의 확인을 거친다.

## 7. 착수 보강 — 완결성 비평 반영

앞 섹션은 "상한을 숨기지 않기"·"순서 원칙"은 탄탄하나, 착수 문서로서 아래를 명시해야 실행 가능해진다.

### 7.1 §3(Now)와 §6(게이트)의 정합 — 모순 해소
§3은 분류 엔진을 P0(지금)로, §6은 M0(엑셀로 가치 증명)을 엔진 build 앞 게이트로 둔다. 정합 규칙:
- **P0-1의 첫 형태 = M0의 '측정 도구' 그 자체다.** 신용카드 150건 + 엑셀 3개에 돌려 미추천율·적중률을 재는 **얇은 프로토타입**.
  사전·미추천 큐 UI 같은 **정식화는 M1**(게이트 통과 후).
- **되돌림 경로(명시):** M0가 **no-go**(다른 자료도 미추천 낮고 4종 합산 절감이 작음)면 **M1을 짓지 않는다.** 우선순위를
  B(자료요청 앱)로 옮긴다. 게이트는 말뿐이 아니라 "M1 착수/중단"이라는 실제 분기다.

### 7.2 M0을 착수 가능하게 — 측정법 3개 (가장 큰 구멍)
1. **'미추천'을 자료형별로 재정의.** '미추천'은 WEHAGO **신용카드** 추천엔진 산출물이다. 통장·세금계산서·현금영수증엔
   그 개념이 그대로 없다(특히 통장은 사업자번호·가맹점이 없음). → 우리는 각 엑셀에서 **"재사용 가능한 과거 결정 키가 없는 라인"**
   비율로 측정한다: (a) 세금계산서·현금영수증은 **사업자번호 이력 매칭**으로 무이력 라인 비율, (b) 통장은 **적요→계정 규칙 커버리지**로
   별도 측정(매칭 키가 약함을 한계로 명시). 이 정의가 없으면 M0는 착수 불가였다.
2. **시간은 엑셀로 못 잰다 → baseline 실측.** 아버지께 **1신고주기 타임로그**(미추천 처리에 쓴 분)를 부탁하거나 1회 관찰 계측.
   이 값이 "절감"의 분모다(지금은 추산 월 5시간뿐).
3. **숫자 go/no-go.** 예시 기준(아버지 답으로 조정): **4종 합산 추정 절감 ≥ 월 10시간 AND 미추천율이 카드(26%)와 유사(≥ ~15%)** → M1 착수.
   미만이면 재타깃. '비슷하다'를 숫자로 못 박아야 M0가 끝나고 판단이 선다.

### 7.3 KPI 보강 (비평: 절반이 목표선 없음 / 오추천 지표 부재)
- **baseline 우선 실측**(7.2) — 절감은 도입 前 시간이 있어야 잰다.
- **오추천율(가장 중요, 신설):** 자동추천을 승인했는데 **사후 수정·경정된 비율.** 세무는 정확성이 생명 — '틀렸는데 통과'를 재는 지표.
  목표: **오추천율 특정 % 이하(예: <1%)로 관리**, 초기엔 전건 실무자 확인.
- **채택률/실사용:** 아버지가 실제로 주기적으로 쓰는가(단일 사용자 도구의 성패 지표).
- **'97% 적중'의 분모 정의:** 이 값은 **거래처(코드) 이력이 있는 부분집합** 위에서 잰 것이다. KPI "97% 유지"는 그 부분집합 기준으로만 성립.

### 7.4 법적 가드레일 추가 (§6.6에 더함 — 비평: 모든 항목에 균일하지 않음)
- **앱 자체의 개인정보 처리 근거(최대 누락).** 이 앱은 수임처 **대표자·담당자 등 제3자 개인정보**를 클라우드(Supabase)에 저장한다.
  → **처리위탁(위수탁) 계약**(세무사=위탁자 ↔ 앱=수탁자) · **개인정보 처리방침** · **저장 위치/국외이전 여부(Supabase 리전)** 를 문서화.
  `pii_enc` 암호화는 **보안 통제일 뿐 처리 근거(legal basis)와 다르다.**
- **카톡 자동 독촉의 법적 차원.** 자동 발송/광고성 메시지는 **정보통신망법**과 **Kakao 비즈메시지 API 약관** 대상 가능 →
  초기엔 **수동 발송/승인 템플릿** 전제, 완전 자동은 확인 후.
- **PDF 두 구멍.** (a) PDF **취득 경로**(카드사/홈택스 다운로드)는 로컬 변환과 별개로 약관 대상 — "로컬이라 무관"으로 뭉개지 말 것.
  (b) 증빙 PDF에 주민번호가 섞일 수 있음 → OCR 파이프라인에 **주민번호 검출·마스킹 필터** 명시(스키마에 컬럼이 없어도 추출 단에서 걸러야).
- **국세청 오픈API 주체.** 어느 계정·인증으로 호출하는지, **bulk 조회가 이용약관상 허용**인지 확인 후 사용.

### 7.5 공수 · capacity (1인 개발자 전제)
개발자가 아들 1인으로 보인다. 범위(엔진+앱+수집)를 순차로 잡는다(병행 지양). **대략 초안**(아버지 답 이후 확정):
| 단계 | 대략 공수 | 비고 |
|---|---|---|
| M0 | 1~2주 | 엔진 프로토타입 + 엑셀 3개 분석 + baseline 타임로그 |
| M1 | 3~5주 | 사전·미추천 큐 UI·13컬럼 출력 |
| M2 | 2~3주 | 자료요청·독촉(스키마 이미 존재) |
| M3 | 미정 | **WEHAGO 개별약관 재확인 후에만** 착수 |

### 7.6 워크플로 마찰 검증 (M0에 포함)
엔진이 엑셀을 뱉으면 아버지가 WEHAGO에 `불러오기` 해야 한다. **이 왕복이 현행 일괄변경(B-2)보다 실제로 빠른지**를
M0에서 **1회 왕복 실측**으로 확인한다. "시간 절감"의 전제가 여기 걸린다 — 왕복이 더 번거로우면 출력 형식을 재설계.
