## 개선안 ① 고객 아이덴티티·병합 키 정비 — 카드 분열·이중집계 차단  ★최우선

**문제(근거):**
- 고객 카드 키가 `no:{custno}` 없으면 `np:{name}|{phone}` (import_handsos.py:182–184).
  같은 손님이 어떤 방문엔 custno 가 있고 어떤 방문엔 없으면 **카드가 2장으로 갈라진다**
  → 방문횟수·누적매출·리핏 상태·VIP 판정이 전부 반씩 쪼개져 왜곡.
- 레코드 dedup 키에 `price·memo` 포함(223–227). 핸드SOS에서 나중에 메모/금액을 수정하면
  **같은 방문이 신·구 2건으로 남아 매출 이중집계**.
- 익명 손님(손님/비회원…)이 같은 날 같은 시술·금액이면 dedup 으로 **1건으로 합쳐져 매출 과소집계**(46–47, 179).
- `custno.lstrip("0")` 으로 custno "0" 이 빈 값이 됨(155).

**개선:**
1. 방문 정체성을 `(date, custno)` 기반으로 승격하고, 동일 방문의 memo/price 변경은
   "새 레코드"가 아니라 **최신값으로 갱신**(스크랩 시각 우선).
2. 임포트 후 **화해(reconcile) 패스**: `np:` 카드의 (이름,전화)가 `no:` 카드와 일치하면 병합,
   병합 로그를 남겨 컨시어지가 확인.
3. 익명 레코드에 행 순번(seq)을 붙여 붕괴 방지.

**효과:** 고객관리의 근간 수치(방문·매출·리핏)가 흔들리지 않게 됨. **모든 상위 기능이 이 위에 서 있다.**

## 개선안 ② 이미 갖고 있는 필드 살리기 — 이전방문·담당·시간, 그리고 생일

**문제(근거):**
- CSV 에는 `이전방문`·`담당`이 들어오는데 `parse_rows` 가 **버린다**(125–165; 담당은 필터로만 소비, 141).
- `stats.py` 가 `time` 을 읽어 피크시간을 내지만(103, 124) 임포트가 **time 을 안 채워서
  '바쁜 시간대' 통계가 핸드SOS 데이터에선 사실상 죽어 있음**(\_date 가 날짜만 취함, 102–110).
- **생일은 어디서도 수집 안 됨** → 생일 알림(build_app.py:131–133)이 수동입력 고객에만 동작.
  케어리스트 1순위(bday)가 실질 비활성.

**개선:**
1. `날짜` 문자열에서 시각을 분리해 `time` 채우기(파서 1줄 거리) → 피크시간 통계 부활.
2. `담당`을 레코드에 보존 → 멀티 디자이너 샵 온보딩 시 디자이너별 성과 분리(확장 대비).
3. `이전방문`을 리핏 갭 검증용 크로스체크로 활용(우리 계산과 어긋나면 병합 문제 신호 — ①의 감지기).
4. 고객상세(또는 고객관리 내보내기)에서 **생일 1회 수집** → 이미 만들어진 생일 케어 경로에 불붙이기.

**효과:** 새 인프라 없이 **이미 흐르는 데이터로** 통계 정확도 + 생일 케어(컨시어지 서비스의 킬러 순간)를 켠다.

## 개선안 ③ '조용한 부분성공' 제거 — 발견케어의 정직성 원칙을 파이프라인에도

**문제(근거):**
- 페이지네이션이 중간에 멈추면 `pagination-stalled` 로 **부분 데이터가 그대로 성공 임포트**
  (harvest.js:131 → sync_one 은 통과, 콘솔에 `(부분수집…)` 출력뿐, handsos_sync.py:378·417).
- **로그인 실패와 '진짜 0행'을 구분 못 함** — 로그인 성공 단언이 없어서(227–232) 비번 오류도 `"0행"` 실패로 보임.
- 예외 경로에선 실패 DOM 을 캡처하지 않음(캡처는 no-table 경로만, 313–328 vs 344–347).

**개선:**
1. 페이지의 `총 N개`(이미 파싱함)와 수집행 수를 **대사(reconcile)** — 미달이면 status 에 `partial` 기록
   + notify + 다음 run 에서 이어받기.
2. 로그인 직후 **성공 마커 단언**(예: 로그아웃 링크/상단 프레임) → "로그인 실패"를 별도 오류로 승격.
3. 예외 시에도 `_capture_failure` 호출 → 자가치유(④)의 입력이 풍부해짐.

**효과:** "다 들어왔다"를 믿을 수 있게 됨. 발견케어에서 세운 **측정=정직** 원칙(미측정≠0)과 동일한 기준.
부분 데이터로 케어리스트가 조용히 틀리는 사고를 구조적으로 차단.

## 개선안 ④ 셀렉터 단일화 + 자가치유 자동 루프 — 유지보수 리스크 흡수

**문제(근거):**
- 셀렉터 진실이 **3곳**(DEFAULT\_LOGIN handsos_sync.py:186–190 · heal.py CURRENT 29–36 ·
  stores.example.yaml)에 흩어지고, 치유 결과는 **4번째 위치**(secrets/{slug}.selectors.yaml)에 쓰임.
  한 곳만 고치면 어긋난다(이미 `_fill` 중복정의 같은 부식 흔적, 177–182).
- 치유는 수동 `--apply` + 사람이 재실행. UI 변경(문서에 명시된 1순위 리스크, SYNC.md §6) 때마다 사람 개입.
- **브라우저 층·harvest.js 테스트 0개** — 그런데 실패 DOM 스냅샷(`_raw/fail_*`)은 이미 쌓이고 있음.

**개선:**
1. 셀렉터를 **canonical 한 곳**(모듈 or YAML)으로 모으고 sync·heal·문서가 전부 그걸 읽게.
2. 자가치유를 루프로: 연속 N회 실패 → heal 자동 실행 → 제안 셀렉터로 **검증 재수확(행수 비교)**
   → 통과 시에만 자동 적용 + 알림. (지금은 제안→사람→적용→재실행 4단계)
3. 이미 캡처된 **실패 HTML 스냅샷을 픽스처**로 harvest.js·프레임 탐색 회귀 테스트 신설 —
   0% 커버리지인 층을 실물 DOM 으로 테스트.

**효과:** "핸드SOS UI 바뀌면?"이라는 상시 불안(사장님이 직접 제기했던 유지보수 우려)이
사람 개입 없는 감지→치유→검증 루프로 흡수됨.

## 개선안 ⑤ 파이썬/JS 이중 구현 해소 — 매출엔진을 테스트 가능한 한 곳으로

**문제(근거):**
- VIP 티어 임계값이 **파이썬(build_app.py:181–188)과 JS(index.html:945)에 중복** —
  한쪽만 바꾸면 앱과 스냅샷이 조용히 어긋남.
- 리핏 로직도 이중(파이썬 102–125 vs JS 966–981, 'new' 임계 60 vs 프리셋 45/60/90 — 의도적이지만 드리프트 위험).
- **교차판매 규칙은 JS 에만 존재**(index.html:952–964) → pytest 303개가 매출엔진의 핵심 규칙을
  하나도 검증 못 함(build_app.py:213 주석으로 명시된 상태).

**개선:**
1. 임계값·규칙 상수를 **한 곳**(파이썬)에서 정의하고 dist JSON 에 `thresholds` 블록으로 내보내
   앱은 렌더만(민감도 프리셋은 그대로 클라이언트).
2. 교차판매 규칙을 파이썬으로 이식 + 단위테스트(JS 는 표시만) — 규칙 추가/조정이 안전해짐.

**효과:** "VIP 기준 바꿨는데 앱은 그대로"류의 조용한 드리프트 차단. 매출엔진(VIP·교차판매)이
발견케어처럼 **결정적·테스트 가능**해져 규칙을 자신 있게 진화시킬 수 있음.
